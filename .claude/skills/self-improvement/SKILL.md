# Self-improvement from user feedback

Treat user redirection as the primary signal for improving how future work is done in this project. This skill is passive: do not interrupt ordinary work to solicit feedback, announce that you are looking for feedback, or make changes merely because an outcome could be generalized.

## When to update guidance

After a correction or redirection, decide whether it expresses a reusable preference, workflow rule, or project direction:

- A one-off content change or task-specific choice usually belongs only in the current work.
- A repeated preference, explicit request to remember something, or correction that identifies a durable project convention can belong in persistent guidance.
- If the signal is ambiguous and persistence would materially constrain future work, ask one concise question before recording it. Otherwise apply a narrow, reasonable interpretation.

## Where to record it

1. Inspect existing project skills and core direction documents before editing. Prefer the narrowest existing skill or instruction file that governs the behavior.
2. Update an existing source of guidance rather than duplicating the same rule in multiple files. Use core project documentation (such as `AGENTS.md` or an established project direction document) for guidance that applies across the project; use a skill for a specific recurring workflow.
3. Create a new guidance file only when the durable direction has no suitable home and is important enough to guide future work. Keep it short, actionable, and consistent with the project's existing instructions.
4. Preserve the user's intent and the existing scope of each file. Do not turn one correction into a broad rule, erase conflicting guidance without resolving the conflict, or change global/personal settings when the requested improvement is project-specific.

## Applying and reporting an improvement

When the user's direction clearly authorizes a durable correction, make the smallest useful documentation update as part of the current task; do not require another approval for that same update. Continue the requested work using the corrected direction. If the documentation change would alter unrelated workflows or resolve a real conflict with other instructions, ask for clarification before making that broader change.

At the end of the task, briefly identify any persistent guidance you changed and the feedback it captures. If the feedback was task-specific or no safe reusable rule was clear, do not force a documentation change; report that only when it helps explain a decision or the user asked for an update.
